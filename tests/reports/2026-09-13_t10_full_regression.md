五次真实运行（同配置、同机器、顺序不同）：

|---|---|---|---|---|---|---|
| T09 off | 1 | false | 1092 s | 1082.95 | `76638d0f…`（基线） | 0.4192 / 0.4235 / 0.4430 |
| T09 on | 2 | true | 994 s | 985.19 | `76638d0f…`（基线） | 0.4192 / 0.4235 / 0.4430 |
| T10 on1 | 1 | true | **1006 s** | 997.34 | **`51009d69…`（不同）** | 0.4189 / 0.4230 / 0.4431 |
| T10 off | 2 | false | 1083 s | 1074.16 | `76638d0f…`（基线） | 0.4192 / 0.4235 / 0.4430 |
| T10 on2 | 单独 | true | **993 s** | 985.70 | **`51009d69…`（不同）** | 0.4189 / 0.4230 / 0.4431 |

- **速度收益稳定**：off 1083/1092 s vs on 993/994/1006 s → **−8.4% … −9.1%**（三次 on 全部落在
  off 两次之外；历史同配置 off 波动带 1054–1097 s）。
- **结果不稳定**：三次 on 里 1 次复现基线、2 次给出另一个产物（且那 2 次彼此**完全一致**，
  连 CC 都一致）→ on 路径本身是确定的，但它与 off 路径**不是同一个结果**。

服务端时间账（`server_timing.jsonl` 全量聚合，2338 次配准）：

| 运行 | `server_forward` | `server_postprocess` | `server_write_pred` | `server_tail_wait` |
|---|---|---|---|---|
| T09/T10 off | 328.90 / 331.60 s | 126.18 / 127.76 s | 89.59 / 93.25 s | — |
| T10 on1 / on2 | 420.43 / 417.52 s | 167.94 / 165.34 s | 106.25 / 104.38 s | 17.13 s（167 次） |

即：一旦 GPU 被 10 个 worker 压满，把 270 s 的 CPU 尾部挪到后台就能省下 ~90 s 墙钟，
代价是尾部线程与主线程争 CPU（forward +26%、后处理 +32%）。**收益与代价都稳定，唯结果变了。**

### 3.1 首个偏差阶段（按任务卡"偏差处理固定顺序"定位）

1. `chain_fit_1`（链 A）的 24 个 `registration/pred_*.pdb`：**文件名与内容两轮完全相同**（24/24 md5 相同）
   → 模型/配准输出不受尾部流水线影响（与第二节"配准层面逐位一致"一致）。
2. 但**候选枚举顺序变了**（客户端日志）：
   - off：`#8 = pred_chain_A_ed_points_0.301508.pdb`，`#9 = 0.282414`，`#10 = 0.267615`
   - on ：`#8 = 0.282414`，`#9 = 0.267615`，`#10 = 0.268379`，`#11 = 0.301508`
   即同一个候选文件在两次运行里排在**不同批次**；每个候选自身的 CC→优化结果逐条相同
   （如 `0.301508`：0.3784 → 0.4183，两轮一致）。
3. 机制（代码）：`fitting/pipeline.py` 的候选消费循环按 **"新出现的文件"成批**评估——
   `sorted(glob("pred_*.pdb"))` 取差集、`len(new_files) >= batch_size(10)` 才评估一批、
   每轮 `time.sleep(2.5)`。**文件出现的时机**决定批次切分，批次切分决定枚举顺序。
   尾部流水线把写盘从"请求返回前"挪到"后台线程"，正好改变了这个时机。
4. 传播：链 A 的最终 `results/pred_A_1.pdb` 不同（`229d10dd` vs `c2832f48`）→ 链 B 的掩码点数
   差 2 个（`masked_points_0000.txt` 多两点、少一点）→ 链 B 配准输入不同 →
   `cc 0.4235 → 0.4230` → 最终 CIF 不同。
5. 反向确认：off 路径在 10+ 次历史运行（T05–T10）里**每次都复现冻结基线 md5**；
   on2 与 on1 逐位一致 → on 的偏差不是随机噪声，而是"批次边界移动"这一确定性偏移。

### 3.2 质量影响与判定

- 决策未越阈值（A 均被拒、B 均被接受、都是 2 个域），但**产物不同**、B 的 CC 略低
  （0.4230 < 0.4235）→ 按任务卡"不能因速度提升接受未知质量变化"与统一验收
  "最终比较 R/t、CC、候选顺序和接受结果"，**`tail_pipeline` 不提升为默认**。
- 这是**既有**的顺序敏感性（O6：`--num-processes` 也会改变结果）被新开关"扰动"出来的表现，
  不是尾部流水线算错了：模型层完全等价（第二、3.1 节证据）。

## 四、默认项选择（本卡交付结论）

| 配置项 | 默认值 | 是否提升 | 依据 |
|---|---|---|---|
| `geometry_cache_mb` | **512** | 保持 | T05 四轮 A/B 逐位一致；T10 复测 F 见第二节 |
| `inference_mode` + `allow_tf32` | **joint**（TF32 跟随框架） | 保持 | T06/T07/T10：split 无速度收益、改变结果（overlap 0.015 量级），且需新基线 |
| `encoding_cache_mb` | **256**（仅 split 生效） | 保持 | T07：命中 99.6%、模型侧 −24%，端到端无净收益 |
| `hypothesis_chunk` | **0**（原整批路径） | 保持 | T08：chunk=64 逐位一致、峰值显存 −15.6%、墙钟 −3…−7%；T10 交叉复测 −5.4%（两轮同向）；但**端到端未验证** → 交付为可选 |
| `tail_pipeline` | **false**（原路径） | **不提升** | 第三节：−9% 但改变最终产物 |
| `blas_threads` / `seed` / `pool_start_method` | 1 / 7351 / 平台默认 | 保持 | P1/P3（老任务卡） |

**交付的推荐配置（可选、全部可回退）**：
`{"blas_threads": 1, "hypothesis_chunk": 64}`（等价 + 省显存，微基准已验证）；
`{"blas_threads": 1, "tail_pipeline": true}`（−9% 墙钟，但产物与冻结基线不同，需接受新基线后再用）。

## 五、未验证 / 已否决项

1. **O6（候选消费顺序的时序敏感性）**：本卡给出了机制级证据（第三节 3.1），
   但**未修改**消费循环。若要"任何时序扰动下都逐位可复现"，需要把候选枚举改成
   "请求完成后按稳定键（文件名或预测分数）整体排序"——那会改变**现有 off 基线**，
   属独立卡片，需重新冻结基线。
2. `hypothesis_chunk=64` 只做了微基准（T08：72/72 逐位一致、显存 −15.6%、墙钟 −3…−7%；
   T10 交叉复测 −5.4% 两轮同向）；**端到端未验证**，因此不作默认 —— 若要用，建议先按
   本卡第三节的方法跑一次 `test/1` 并比对冻结基线。
3. `inference_mode=split`（±编码缓存）端到端无收益且改变结果 → 明确**不推荐**用于交付路径。
4. 未做：pinned memory / 异步拷贝（任务卡 T09 要求的"传输等待明显后才开"，本轮未出现
   传输瓶颈：G2H 只有 4×4 位姿）；几何/编码与 GPU 的重叠（会与 GPU 竞争且牵涉顺序等价）。
5. `assembly_summary.txt` 的 md5 在多次运行间因**时间戳/路径行**不同而不同（非结构差异），
   与冻结基线比对时只作参考。
